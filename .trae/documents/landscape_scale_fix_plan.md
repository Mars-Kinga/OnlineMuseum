# 地图横屏自适应缩放问题检查与修复计划

## 1. 问题分析

用户反馈在“横屏分辨率下地图的缩放不正确”。

回顾当前的 CSS 实现：
```css
/* 新增地图包裹容器 */
.map-wrapper {
  position: relative;
  height: 100vh;
  width: calc(100vh * 1440 / 1024);
  margin: 0 auto;
}
```

我们的逻辑是：让地图的高度始终等于屏幕高度（`100vh`），然后宽度按照 `1440/1024` 的比例进行计算。
这在竖屏或者屏幕长宽比小于 `1440/1024`（约 `1.406`）的设备上表现很好：地图的高度撑满屏幕，宽度超出屏幕，通过外层的 `.scroll-container` 进行横向滑动。

**但在极宽的横屏下（例如 16:9 或 21:9，屏幕长宽比大于 1.406）会发生什么？**
假设屏幕是 `1920 x 1080`（宽高比 `1.77`）：
- `height` = `1080px`
- `width` = `1080 * 1440 / 1024` = `1518.75px`

此时，地图包裹容器的高度虽然是满屏的，但它的宽度（1518px）却小于屏幕宽度（1920px）。
由于我们设置了 `margin: 0 auto;`，地图会在屏幕中间显示，两边留下大片的空白。
然而，原始的非自适应版本中（`OnlineMuseum_main`），地图是被要求至少覆盖整个屏幕的（背景铺底效果）。在极宽的横屏下，用户期望的可能是地图的宽度至少能撑满屏幕，而不是居中显示并在两边留白。

### 为什么现在的缩放不正确？
如果用户希望在任何设备上地图都不留白，那么我们需要保证地图包裹层：
- **宽度至少等于视口宽度**（`100vw`）
- **高度至少等于视口高度**（`100vh`）
- 并且始终保持 `1440:1024` 的比例。

也就是说，地图包裹容器的尺寸应该是 `cover` 模式：
- 宽度 = `max(100vw, 100vh * 1440 / 1024)`
- 高度 = `max(100vh, 100vw * 1024 / 1440)`

或者，如果允许地图在横屏下宽度撑满，高度超出（产生上下滚动），那么逻辑就应该是这样的。
但根据最初的需求（“按照设备网页高度最大化显示，支持左右滑动”），我们之前的设计其实是符合字面意思的（固定高度，宽度自适应并左右滑动）。
然而，如果屏幕极宽（例如桌面全屏），按高度等比计算出的宽度不足以铺满屏幕时，地图就没有“铺满”背景。

我们需要重新定义 `.map-wrapper` 的尺寸，使其在任何情况下都至少能铺满整个屏幕，同时保持原始比例，以确保交互圆点（基于百分比）不偏移。

**修复思路**：
当屏幕的宽高比（aspect-ratio）**大于** `1440/1024` 时（即超宽屏，如 1920x1080）：
- 宽度应该撑满 `100vw`。
- 高度应该按比例放大，即 `calc(100vw * 1024 / 1440)`。
- 这时高度会大于 `100vh`，需要允许上下滚动（或者隐藏超出的部分，视设计而定）。

当屏幕的宽高比（aspect-ratio）**小于** `1440/1024` 时（即窄屏/竖屏，如手机或平板）：
- 高度应该撑满 `100vh`。
- 宽度应该按比例放大，即 `calc(100vh * 1440 / 1024)`。
- 这时宽度会大于 `100vw`，允许左右滑动（这是目前已实现的功能）。

这其实就是 CSS `object-fit: cover` 或者 `background-size: cover` 的行为。
由于我们需要容器本身具有这个尺寸（以便百分比定位的点能正确分布），我们可以使用 CSS 的 `max()` 函数或者 CSS 媒体查询结合 `aspect-ratio`。

### 方案 1：使用 CSS `max()`（推荐）
```css
.map-wrapper {
  position: relative;
  /* 宽度取 100vw 和 基于 100vh 计算出宽度的最大值 */
  width: max(100vw, calc(100vh * (1440 / 1024)));
  /* 高度取 100vh 和 基于 100vw 计算出高度的最大值 */
  height: max(100vh, calc(100vw * (1024 / 1440)));
  margin: 0 auto;
}
```
这样设置后：
- 在超宽屏下：`100vw` 会大于 `100vh * 1440/1024`，所以 `width` 为 `100vw`。对应的高 `100vw * 1024/1440` 也会大于 `100vh`，所以 `height` 变为放大后的高度。比例完美保持为 1440:1024，无白边。
- 在窄屏下：`100vh * 1440/1024` 会大于 `100vw`，所以 `width` 放大，产生横向滚动。对应的高 `100vh` 会大于基于 `100vw` 计算的高，所以 `height` 为 `100vh`。比例完美保持为 1440:1024，无白边。

### 同时修复滚动容器
既然在超宽屏下高度可能超出 `100vh`，如果需要能够查看到被截断的底部内容，外层 `.scroll-container` 必须同时允许 `overflow-y: auto;`。如果设计上只允许横向滑动（纵向截断），则保持 `overflow-y: hidden;`，但这可能会导致底部部分国家被截断无法点击。为了安全起见，通常在 `cover` 布局下，如果不希望滚动，就需要接受裁剪；如果希望都能看到，就应该允许滚动。结合之前的需求“支持左右滑动”，如果是超宽屏，可能应该“支持上下滑动”。
最合理的设定是：
```css
.scroll-container {
  width: 100%;
  height: 100vh;
  overflow: auto; /* 自动处理横向或纵向的滚动 */
}
```

## 2. 实施步骤
1. 修改 `/src/screens/Desktop.vue` 中 `.map-wrapper` 的 CSS 规则，使用 `max()` 函数确保其尺寸始终呈 `cover` 模式铺满屏幕，且严格保持 1440:1024 比例。
2. 修改 `.scroll-container`，将 `overflow-x: auto; overflow-y: hidden;` 改为 `overflow: auto;` 以适应横屏时的垂直滚动需求。
3. 验证修改：
   - 在窄屏下（移动端）：高 100vh，宽溢出，可横向滑动。
   - 在超宽屏下（横屏桌面）：宽 100vw，高溢出，可纵向滑动。
   - 交互点始终不错位。
